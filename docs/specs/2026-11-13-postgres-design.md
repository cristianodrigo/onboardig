# Postgres no lugar do SQLite

Data: 2026-11-13

## Objetivo

O onboarding deixa de usar o arquivo SQLite e passa a usar só Postgres, na máquina de desenvolvimento e em produção. Os dados que estão no SQLite do volume de produção são copiados uma vez, com os mesmos ids.

## Decisões

- Produção: serviço novo de Postgres no Dokploy, no mesmo projeto do onboarding.
- Desenvolvimento: Postgres local via Docker Compose. O app não abre mais SQLite.
- Acesso: driver `pg`, SQL nas rotas, sem ORM.
- Cópia: script único lê o arquivo SQLite de produção e grava no Postgres. O SQLite local de demonstração não entra nessa cópia.
- `dados_json` continua `TEXT`. A aplicação segue fazendo `JSON.stringify` na escrita e `JSON.parse` na leitura.
- `ativo` e `revogado` passam a `BOOLEAN`.
- Datas passam a `TIMESTAMPTZ`.

## Arquitetura

Quatro peças, cada uma com um papel.

| Peça | Função | Depende de |
|---|---|---|
| `app/db.js` | Pool, schema na subida, seed do RH, `query`, `withTransaction`, `auditar`, `gerarConvite`, `criarJornadaComChecklist` | `DATABASE_URL` |
| Rotas em `app/routes/` | As mesmas rotas de hoje, assíncronas, SQL no dialeto Postgres | `db.js` |
| `app/scripts/migrar-sqlite.mjs` | Cópia única do arquivo SQLite para o Postgres | `SQLITE_PATH`, `DATABASE_URL` |
| `docker-compose.yml` na raiz do repositório | Postgres só para desenvolvimento | nada do app |

`query(sql, params)` devolve as linhas. `withTransaction(fn)` entrega um cliente e confirma ou desfaz. Os placeholders são `$1`, `$2`. O id novo vem de `RETURNING id`.

Não há fallback para SQLite. Sem `DATABASE_URL`, o processo termina antes de escutar a porta e o log não mostra a senha da URL.

## Modelo

As cinco tabelas e os relacionamentos permanecem. Chave primária: `INTEGER GENERATED BY DEFAULT AS IDENTITY`, para a cópia poder informar o id. Chaves estrangeiras sem `ON DELETE CASCADE`. Não existe exclusão de usuário hoje; desativar continua sendo `ativo = false`.

| Tabela | Colunas que mudam de tipo |
|---|---|
| `users` | `ativo BOOLEAN NOT NULL DEFAULT true`; `criado_em TIMESTAMPTZ NOT NULL DEFAULT now()`; `cpf TEXT` |
| `jornadas` | `criado_em TIMESTAMPTZ NOT NULL DEFAULT now()` |
| `documentos` | `enviado_em TIMESTAMPTZ`; `dados_json TEXT NOT NULL DEFAULT '{}'` |
| `convites` | `criado_em`, `expira_em`, `usado_em` como `TIMESTAMPTZ`; `revogado BOOLEAN NOT NULL DEFAULT false` |
| `auditoria` | `criado_em TIMESTAMPTZ NOT NULL DEFAULT now()`; `autor_id` pode ser nulo |

Restrições que continuam: `users.email` único; `jornadas.user_id` único; `documentos (jornada_id, tipo)` único; `convites.token` único; `papel` em `candidato` ou `rh`; `status` em `pendente`, `em_revisao`, `devolvido`, `aprovado`.

`datetime('now')` vira `now()`. `datetime('now', '+7 days')` vira `now() + interval '7 days'`. Comparar validade do convite é `expira_em > now()`.

O schema é aplicado na subida com `CREATE TABLE IF NOT EXISTS`. A coluna `cpf` entra no `CREATE TABLE`, sem `ALTER` separado.

## Seed

Igual à regra atual. Se já existe usuário, o seed não faz nada. Se o banco está vazio e `SEED_RH_EMAIL` e `SEED_RH_PASSWORD` existem, cria um RH e registra auditoria com `autor_id` nulo. `SEED_RH_NOME` vazio vale `RH`. Se o banco está vazio e essas variáveis faltam, o processo sobe e registra um aviso. Não cria usuário.

## Cópia

Ordem, numa transação só: `users`, `jornadas`, `documentos`, `convites`, `auditoria`. Os ids do SQLite são preservados. No fim, cada sequence fica em `max(id)`.

O script lê `SQLITE_PATH` e escreve em `DATABASE_URL`. Se o arquivo não existe, termina com erro e não grava nada. Se qualquer tabela de destino já tem linha, termina com erro e não grava nada. Uma falha no meio desfaz a transação.

Ordem da virada em produção:

1. Criar o Postgres no Dokploy e anotar a `DATABASE_URL` interna.
2. Rodar o script com o SQLite do volume `onboarding-sqlite` (`/data/onboardig.db`) e essa URL.
3. Só então apontar o app para essa URL e publicar.
4. Na subida, o seed vê usuários e não cria outro RH.

Se o app subir antes da cópia, o seed cria o RH e a cópia se recusa a rodar. A recuperação é esvaziar as tabelas do Postgres e rodar o script de novo, com o app parado.

## Falhas em execução

- Criar candidato (usuário, jornada, documentos, convite, auditoria) é uma transação. O e-mail sai depois do commit. Falha de SMTP não desfaz o usuário; a resposta continua com `email_enviado: false`.
- Qualquer rota com duas ou mais escritas usa `withTransaction`.
- E-mail duplicado continua `409`. Falha inesperada de banco vira `500` com mensagem genérica; o detalhe fica no log.
- Postgres indisponível no meio do pedido: `503`.
- Pool com no máximo 10 conexões.

## Desenvolvimento

`docker compose up -d` sobe o Postgres local. `DATABASE_URL` no `.env` aponta para ele. `.env.example` documenta a variável e deixa de tratar `DATABASE_PATH` como banco do app. O volume SQLite de produção permanece só como origem da cópia e como cópia de segurança até a conferência.

## Testes

Node 24, `node:test`, contra um banco do Compose cujo nome termina em `_test`. Os testes recusam outra URL.

- Seed: banco vazio com as variáveis do RH cria um usuário; a segunda subida não duplica.
- Cópia: um SQLite pequeno com uma linha em cada tabela reaparece no Postgres com os mesmos ids; a segunda execução termina com erro e não altera as linhas.
- Os scripts `test-upload.mjs`, `test-catalogo.mjs`, `test-convite.mjs` e `test-azure-upload.mjs` deixam de abrir `onboardig.db`. A limpeza de dados de teste usa o Postgres.

Conferência manual depois da virada: login do RH, listagem de usuários e contagem igual à do SQLite de origem.

## Fora de escopo

Sessão em Postgres, ORM, copiar o SQLite local de demonstração, mudar o Azure Blob, apagar o volume SQLite nesta entrega.
